# Phần III — UI Architecture

# Buổi 31 — Dependency Injection

Ở Buổi 30, chúng ta đã có:

```text
Controller
    ↓
Service
    ↓
Repository Interface
    ↓
SQLite Repository
    ↓
Database
```

Nhưng xuất hiện một câu hỏi rất quan trọng:

> **Ai tạo các object này?**

Ví dụ:

```python
repository = SQLiteStoryRepository(...)
service = StoryService(repository)
controller = StoryController(view, service)
```

Nếu mỗi class tự tạo dependency của mình thì architecture sẽ nhanh chóng trở nên khó kiểm soát.

Hôm nay chúng ta học **Dependency Injection — DI**.

---

# 1. Mental Model

Trước tiên hãy hiểu một câu:

> **Dependency Injection không phải là một framework. Nó là cách truyền dependency từ bên ngoài vào object thay vì để object tự tạo dependency.**

Ví dụ **không dùng DI**:

```python
class StoryService:

    def __init__(self):
        self.repository = SQLiteStoryRepository()
```

`StoryService` tự tạo:

```text
StoryService
     │
     └── tạo SQLiteStoryRepository
```

Nó bị phụ thuộc trực tiếp vào SQLite.

---

Dùng DI:

```python
class StoryService:

    def __init__(self, repository):
        self.repository = repository
```

Bên ngoài:

```python
repository = SQLiteStoryRepository()
service = StoryService(repository)
```

Bây giờ:

```text
Composition Root
      │
      ├── tạo Repository
      │
      └── inject
            ↓
        StoryService
```

Đây chính là Dependency Injection.

---

# 2. Dependency là gì?

Dependency đơn giản là:

> Một object cần một object khác để hoạt động.

Ví dụ:

```python
class StoryService:

    def __init__(self, repository):
        self.repository = repository
```

`StoryService` phụ thuộc vào:

```text
repository
```

Ta gọi:

```text
repository = dependency
```

Còn:

```text
StoryService = dependent object
```

---

# 3. Dependency Graph

Trong application của chúng ta:

```text
MainWindow
    ↓
Controller
    ↓
StoryService
    ↓
StoryRepository
    ↓
DatabaseManager
```

Đây là một **dependency graph**.

Ví dụ:

```text
StoryController
      │
      ▼
 StoryService
      │
      ▼
StoryRepository
      │
      ▼
DatabaseManager
```

Object phía trên cần object phía dưới.

# 6. Constructor Injection

Đây là kiểu DI phổ biến nhất trong Python.

```python
class StoryService:

    def __init__(
        self,
        repository,
    ):
        self.repository = repository
```

Inject:

```python
service = StoryService(
    repository
)
```

Ưu điểm:

* dependency rõ ràng
* object luôn ở trạng thái hợp lệ
* dễ test
* dễ đọc
* không cần magic

Đây là kiểu tôi khuyên bạn sử dụng mặc định.

# 7. Dependency Injection không phải Magic

Không cần:



Chỉ vậy thôi.

# 8. Interface + DI

Buổi 30 chúng ta có:

```python

class StoryRepository(ABC):

    @abstractmethod
    def save(self, story):
        ...

    @abstractmethod
    def get(self, story_id):
        ...
```

Service:

```python
class StoryService:

    def __init__(
        self,
        repository: StoryRepository,

        self.repository = repository
```

Bây giờ Service không quan tâm implementation.

Có thể inject:

```text
SQLiteStoryRepository
```

hoặc:

```text
FakeStoryRepository
```

hoặc:

```text
PostgresStoryRepository
```

# 11. Constructor Injection vs Method Injection

Có thể inject dependency qua method:

```python
class StoryService:

    def create_story(
        self,
        title,
        repository,
    ):
        ...
```

Nhưng thường không tốt nếu Repository là dependency lâu dài.

Tốt hơn:

```python
class StoryService:

    def __init__(self, repository):
        self.repository = repository

    def create_story(self, title):
        ...
```

Rule đơn giản:

> Nếu object cần dependency trong suốt lifetime → Constructor Injection.

---

# 12. Setter Injection

Có thể:

```python
class StoryService:

    def set_repository(self, repository):
        self.repository = repository
```

Nhưng có vấn đề:

```python
service = StoryService()

service.create_story(...)
```

Có thể `repository` chưa được inject.

Object có trạng thái không hợp lệ.

Vì vậy trong Python application architecture:

> **Ưu tiên Constructor Injection.**

# 13. Composition Root

Đây là khái niệm rất quan trọng.

**Composition Root** là nơi application tạo và kết nối các dependency.

Ví dụ:

```text
main.py
```

```python
def main():

    connection = create_database()

    repository = SQLiteStoryRepository(
        connection
    )

    service = StoryService(
        repository
    )

    window = MainWindow()

    controller = StoryController(
        window,
        service,
    )

    window.show()

    app.exec()
```

`main.py` chính là nơi:

```text
compose application
```

---

# 14. Tại sao cần Composition Root?

Không có Composition Root:

```text
View
 └── tạo Controller

Controller
 └── tạo Service

Service
 └── tạo Repository

Repository
 └── tạo Database
```

Dependency creation nằm khắp nơi.

Có Composition Root:

```text
                 main.py
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    Database    Repository     Service
                                 │
                                 ▼
                            Controller
                                 │
                                 ▼
                                View
```

Một nơi chịu trách nhiệm wiring.

# 25. DI Container là gì?

Khi application rất lớn, dependency graph có thể dài:

```text
A
 ↓
B
 ↓
C
 ↓
D
 ↓
E
```

Có thể sử dụng DI Container.

Concept:

```python
container.register(
    StoryRepository,
    SQLiteStoryRepository,
)
```

Sau đó:

```python
service = container.resolve(
    StoryService
)
```

Container tự xây dependency graph.

# 38. Anti-pattern: Service Locator

Một anti-pattern phổ biến:

```python
class StoryService:

    def create_story(self, title):

        repository = ServiceLocator.get(
            "story_repository"
        )

        ...
```

Nhìn có vẻ tiện.

Nhưng dependency bị ẩn.

Ta nhìn constructor:

```python
StoryService()
```

không biết nó cần gì.

Trong khi:

```python
StoryService(repository)
```

nói rất rõ:

> Tôi cần Repository.

Vì vậy:

> **Explicit Dependency > Hidden Dependency**

---

# 39. Anti-pattern: Global Dependency

Ví dụ:

```python
repository = SQLiteStoryRepository(...)
```

global.

Sau đó:

```python
class StoryService:

    def create_story(self, title):
        repository.save(...)
```

Đây là hidden global dependency.

Testing trở nên khó.

Tốt:

```python
class StoryService:

    def __init__(self, repository):
        self.repository = repository
```

---

# 40. Anti-pattern: Dependency Creation trong Domain

Không nên:

```python
class Story:

    def save(self):
        repository = SQLiteStoryRepository()
        repository.save(self)
```

Domain không nên biết persistence.

Domain:

```python
class Story:

    def publish(self):
        ...
```

Repository:

```python
repository.save(story)
```

# 41. Một nguyên tắc rất mạnh

Hãy tìm tất cả:

```python
ClassName(...)
```

trong application.

Hỏi:

> **Class này có đang tự tạo dependency không?**

Ví dụ:

```python
class StoryService:

    def __init__(self):
        self.repository = SQLiteStoryRepository()
```

Nếu có, cân nhắc DI.

Nhưng không phải mọi `ClassName(...)` đều là dependency injection violation.

Ví dụ:

```python
story = Story(title)
```

hoàn toàn bình thường.

`Story` là object mà Service đang tạo để thực hiện use case.


## Chuẩn bị cho Buổi 32 — Application State

Buổi tiếp theo sẽ giải quyết một vấn đề bắt đầu xuất hiện trong ứng dụng lớn:

```text
User đăng nhập
Story hiện tại
Chapter hiện tại
Search keyword
Filter
Pagination
Theme
Download progress
Crawl status
```

Nếu mỗi widget tự giữ state:

```text
Widget A → state
Widget B → state
Widget C → state
Controller → state
```

thì state rất dễ bị phân tán.

Buổi 32 chúng ta sẽ xây:

```text
                 Application
                     State
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Story       Chapter      UI State
        State       State
          │           │
          └──────┬────┘
                 ▼
              PySide6
```

và đặc biệt sẽ phân biệt **UI State, Application State và Domain State** — đây là nền tảng rất quan trọng trước khi chúng ta bước sang **Event Bus ở Buổi 33**.
