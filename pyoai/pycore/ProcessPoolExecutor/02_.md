# Buổi 2 — Process vs Thread: GIL và CPU-bound

Hôm nay ta đi vào **lý do cốt lõi** khiến `ProcessPoolExecutor` tồn tại.

Mục tiêu:

```text
ThreadPoolExecutor
        │
        ├── Thread
        ├── Shared Memory
        └── GIL
              │
              ▼
       CPU-bound bị giới hạn

ProcessPoolExecutor
        │
        ├── Process riêng
        ├── Memory riêng
        └── mỗi process có Python interpreter riêng
              │
              ▼
       có thể chạy CPU-bound song song
```

---

# 1. Trước hết: CPU-bound là gì?

Một chương trình CPU-bound là chương trình mà phần lớn thời gian dành cho việc tính toán.

Ví dụ:

```python
def cpu_task(n):
    total = 0

    for i in range(n):
        total += i * i

    return total
```

Ở đây CPU phải liên tục thực hiện:

```text
load
+
multiply
+
add
+
loop
+
...
```

Không phải chờ network hay disk.

---

# 2. I/O-bound khác CPU-bound

### I/O-bound

Ví dụ:

```python
def download():
    requests.get(url)
```

CPU có thể phải chờ:

```text
CPU
 │
 ├── gửi request
 │
 └── WAIT ---------------------- response
```

Trong lúc chờ, thread khác có thể chạy.

Vì vậy:

```text
I/O-bound
    ↓
ThreadPoolExecutor
```

thường rất hiệu quả.

---

### CPU-bound

Ví dụ:

```python
def calculate():
    for _ in range(100_000_000):
        ...
```

CPU luôn bận:

```text
CPU █████████████████████████████
```

Ở đây ta muốn:

```text
Core 1 → calculate A
Core 2 → calculate B
Core 3 → calculate C
Core 4 → calculate D
```

Đó chính là nơi ProcessPool phát huy tác dụng.

---

# 3. GIL là gì?

Trong **CPython**, GIL — Global Interpreter Lock — là một lock liên quan đến việc thực thi Python bytecode.

Có thể hình dung đơn giản:

```text
Process
│
├── Thread A
├── Thread B
├── Thread C
└── Thread D
        │
        ▼
       GIL
        │
        ▼
   Python bytecode
```

Một cách đơn giản hóa:

```text
Thread A → giữ GIL → chạy
Thread B → chờ
Thread C → chờ
Thread D → chờ

Thread A → nhả GIL

Thread B → giữ GIL → chạy
```

Vì vậy nhiều Python threads không đồng nghĩa với việc một workload CPU-bound Python sẽ chạy bytecode Python đồng thời trên nhiều core.

> Lưu ý: GIL là chi tiết của CPython; Python hiện nay cũng có các build/configuration mới như free-threaded CPython, nhưng khi học `ProcessPoolExecutor`, mô hình GIL truyền thống vẫn là nền tảng quan trọng.

---

# 4. ThreadPoolExecutor thử CPU-bound

Hãy tạo benchmark.

```python
from concurrent.futures import ThreadPoolExecutor
import time


def cpu_task(n):
    total = 0

    for i in range(n):
        total += i * i

    return total


numbers = [10_000_000] * 4


start = time.perf_counter()

for n in numbers:
    cpu_task(n)

end = time.perf_counter()

print("Sequential:", end - start)
```

Đây là baseline.

---

# 5. ThreadPoolExecutor

```python
from concurrent.futures import ThreadPoolExecutor
import time


def cpu_task(n):
    total = 0

    for i in range(n):
        total += i * i

    return total


numbers = [10_000_000] * 4


start = time.perf_counter()

with ThreadPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(cpu_task, numbers))

end = time.perf_counter()

print("Thread:", end - start)
```

Bạn có thể kỳ vọng rằng:

```text
4 tasks
+
4 threads
=
4x faster
```

nhưng thực tế thường **không xảy ra** với CPU-bound Python code.

Có thể thấy:

```text
Sequential: 2.7s
Thread:     2.8s
```

hoặc thậm chí thread chậm hơn.

---

# 6. Tại sao Thread không tăng tốc?

Có hai vấn đề chính:

### 1. GIL

Các thread tranh quyền thực thi Python bytecode.

### 2. Thread switching

Python phải chuyển đổi giữa các thread.

Ví dụ:

```text
Thread A
   ↓
Thread B
   ↓
Thread C
   ↓
Thread D
   ↓
Thread A
```

Việc scheduling/switching này có overhead.

Do đó với workload:

```text
CPU-bound
+
pure Python
```

thread pool thường không đem lại scaling như mong đợi.

---

# 7. ProcessPoolExecutor

Bây giờ thử process.

```python
from concurrent.futures import ProcessPoolExecutor
import time


def cpu_task(n):
    total = 0

    for i in range(n):
        total += i * i

    return total


if __name__ == "__main__":

    numbers = [10_000_000] * 4

    start = time.perf_counter()

    with ProcessPoolExecutor(max_workers=4) as executor:
        results = list(executor.map(cpu_task, numbers))

    end = time.perf_counter()

    print("Process:", end - start)
```

Có khả năng bạn sẽ thấy:

```text
Sequential: 2.7s
Thread:     2.8s
Process:    0.9s
```

Nhưng **đừng mong con số chính xác như vậy**.

# 8. Vì sao Process có thể nhanh hơn?

Hãy hình dung CPU 4 core:

```text
┌──────────────────────────┐
│           CPU            │
│                          │
│ Core 1   Core 2          │
│   │        │             │
│   ▼        ▼             │
│ Proc 1   Proc 2          │
│                          │
│ Core 3   Core 4          │
│   │        │             │
│   ▼        ▼             │
│ Proc 3   Proc 4          │
└──────────────────────────┘
```

Mỗi process có:

```text
Python interpreter
+
memory space
+
execution state
```

riêng.

Vì vậy:

```text
Process 1 → Core 1
Process 2 → Core 2
Process 3 → Core 3
Process 4 → Core 4
```

có thể thực sự chạy song song.

# 9. GIL nằm ở đâu?

Đây là điểm cực kỳ quan trọng.

Ta có:

```text
Process 1
└── Python interpreter
    └── GIL #1

Process 2
└── Python interpreter
    └── GIL #2

Process 3
└── Python interpreter
    └── GIL #3

Process 4
└── Python interpreter
    └── GIL #4
```

Không phải:

```text
Process 1 ─┐
Process 2 ─┤
Process 3 ─┼── một GIL duy nhất
Process 4 ─┘
```

Đó là lý do ProcessPool có thể vượt qua giới hạn GIL của một interpreter.

---

# 10. Nhưng Process không miễn phí

Đây là phần rất quan trọng.

Ta không thể kết luận:

> Process luôn nhanh hơn Thread.

Không.

Process có overhead:

```text
create process
       ↓
serialize arguments
       ↓
IPC
       ↓
execute
       ↓
serialize result
       ↓
IPC
       ↓
deserialize result
```

Ví dụ task:

```python
def square(x):
    return x * x
```

thì:

```text
process overhead
>>>>>>>>>>>>>>>>>>>>>
x * x
```

Có thể xảy ra.

---

# 11. Task càng lớn, Process càng đáng giá

Giả sử:

```text
Task A = 1 microsecond
```

thì ProcessPool rất tệ.

Nhưng:

```text
Task A = 2 seconds CPU
```

thì overhead tương đối nhỏ.

Ta có:

```text
┌──────────────────────────────┐
│ Process overhead             │
│ █                            │
│                              │
│ CPU computation              │
│ ████████████████████████████ │
└──────────────────────────────┘
```

Đây là nguyên tắc:

> **ProcessPool phù hợp với những task đủ lớn để amortize process/serialization overhead.**

---

# 12. Amdahl's Law

Khi làm parallel programming, một khái niệm rất quan trọng là **Amdahl's Law**.

Giả sử chương trình có:

```text
80% parallelizable
20% sequential
```

Dù bạn có:

```text
100 CPU cores
```

phần sequential vẫn giới hạn speedup.

Công thức:

```text
Speedup = 1 / ((1 - P) + P / N)
```

Trong đó:

```text
P = phần có thể parallel
N = số worker
```

Ví dụ:

```text
P = 0.8
N = 4
```

thì:

```text
Speedup = 1 / (0.2 + 0.8/4)
        = 1 / 0.4
        = 2.5
```

Không phải 4x.

# 14. Benchmark 3 mô hình

Hôm nay hãy xây một benchmark nhỏ.

```python
from concurrent.futures import (
    ThreadPoolExecutor,
    ProcessPoolExecutor,
)
import time


def cpu_task(n):
    total = 0

    for i in range(n):
        total += i * i

    return total


def sequential(numbers):
    for n in numbers:
        cpu_task(n)


def threaded(numbers):
    with ThreadPoolExecutor(max_workers=4) as executor:
        list(executor.map(cpu_task, numbers))


def processed(numbers):
    with ProcessPoolExecutor(max_workers=4) as executor:
        list(executor.map(cpu_task, numbers))


def benchmark(name, func, numbers):
    start = time.perf_counter()

    func(numbers)

    elapsed = time.perf_counter() - start

    print(f"{name:<15} {elapsed:.3f}s")


if __name__ == "__main__":

    numbers = [10_000_000] * 4

    benchmark(
        "Sequential",
        sequential,
        numbers,
    )

    benchmark(
        "ThreadPool",
        threaded,
        numbers,
    )

    benchmark(
        "ProcessPool",
        processed,
        numbers,
    )
```

Có thể thu được kiểu:

```text
Sequential      2.500s
ThreadPool      2.600s
ProcessPool     0.800s
```

Nhưng kết quả phụ thuộc:

* CPU
* Python version
* OS
* số core
* power mode
* background processes
* workload

# 16. Nhiều process không đồng nghĩa nhanh hơn

Ví dụ CPU có:

```text
4 cores
```

nhưng bạn tạo:

```text
32 processes
```

thì:

```text
32 processes
      │
      ▼
4 cores
```

CPU phải scheduling rất nhiều process.

Có:

```text
context switching
+
memory pressure
+
IPC
+
scheduler overhead
```

Do đó:

```text
workers ↑
```

không có nghĩa:

```text
performance ↑ vô hạn
```

# 17. Một nguyên tắc thực tế

Với CPU-bound workload thuần Python:

```text
workers ≈ số CPU cores
```

thường là điểm bắt đầu hợp lý.

Sau đó benchmark.

Không nên mù quáng:

```python
max_workers=100
```

cho mọi workload.

# 18. Thread vẫn có lợi thế

Đừng nghĩ sau bài này rằng:

```text
ProcessPool > ThreadPool
```

Trong mọi trường hợp.

Không.

### I/O-bound:

```text
ThreadPoolExecutor
       ↓
   thường phù hợp
```

### CPU-bound:

```text
ProcessPoolExecutor
       ↓
   thường phù hợp
```

Ví dụ crawl website:

```text
HTTP request
HTTP request
HTTP request
HTTP request
```

thường là I/O-bound.

Không nên dùng ProcessPool chỉ vì:

> "Process chạy parallel."

---

# 19. Một trường hợp đặc biệt

Một số thư viện Python gọi native code và có thể **release GIL**.

Ví dụ một số workload của:

```text
NumPy
OpenCV
Pillow
compression libraries
```

có thể thực hiện phần nặng bên ngoài Python interpreter.

Khi đó:

```text
ThreadPoolExecutor
```

đôi khi cũng có thể tận dụng nhiều core.

Vì vậy quy tắc chính xác hơn là:

> Hãy nhìn vào **bản chất workload và thư viện đang thực hiện workload**, không chỉ nhìn vào tên task.

# 20. So sánh tổng quát

| Đặc điểm         | ThreadPool       | ProcessPool                      |
| ---------------- | ---------------- | -------------------------------- |
| Đơn vị           | Thread           | Process                          |
| Memory           | Shared           | Separate                         |
| GIL              | Có ảnh hưởng     | Mỗi process có interpreter riêng |
| CPU-bound Python | Thường không tốt | Thường tốt                       |
| I/O-bound        | Rất tốt          | Có thể dùng nhưng thường dư thừa |
| Startup          | Nhẹ              | Nặng hơn                         |
| Serialization    | Ít hơn           | Quan trọng                       |
| Communication    | Dễ hơn           | Phức tạp hơn                     |
| Memory           | Thấp hơn         | Cao hơn                          |
| Isolation        | Thấp             | Cao hơn                          |
| Debug            | Dễ hơn           | Khó hơn                          |

# 21. Mô hình tư duy cần nhớ

Đừng học thuộc:

```text
CPU → Process
I/O → Thread
```

Hãy suy nghĩ theo pipeline:

```text
Workload
   │
   ├── CPU-bound?
   │       │
   │       ├── pure Python?
   │       │       ↓
   │       │   ProcessPool
   │       │
   │       └── native code releases GIL?
   │               ↓
   │          Thread có thể phù hợp
   │
   └── I/O-bound

       ThreadPool / asyncio
```

Đây mới là tư duy của người thiết kế hệ thống.
